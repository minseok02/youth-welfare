# 문제 해결 기록

재발할 가능성이 있거나 다음 작업의 판단을 바꾸는 문제만 기록합니다. 원인·변경·실제 검증·미확인 부분을 구분하고, 단순 탐색 실패나 대화 전체는 누적하지 않습니다.

## 환경을 잘못 구분한 점검

- 문제: `run-local-*`, `prod` 프로필, `127.0.0.1:8082`를 보고 로컬 개발 데이터라고 판단하면 앱과 점검 DB가 달라질 수 있습니다.
- 원인: 로컬 Compose와 운영 Compose가 프로필·호스트 포트를 공유하고, smoke의 DB 선택은 별도 설정입니다. 로컬 앱이 RDS를 사용할 수도 있습니다.
- 기준: [환경 안내](environment-guide.md)에서 실행 위치·앱·DB·영향을 먼저 구분합니다. 운영 DB를 확인하려고 로컬 `db` 컨테이너를 새로 띄우지 않습니다.
- 확인 근거: [docker-compose.yml](../../docker-compose.yml), [docker-compose.prod.yml](../../docker-compose.prod.yml), [smoke-common.sh](../../deploy/smoke/smoke-common.sh).
- 이번 작업은 문서 정리이며 서버/DB 상태 변경을 수행하지 않습니다.

## 문서 계약 테스트가 캐시로 생략되는 경우

- 증상: 문서를 바꾼 뒤 `DB_USERNAME=app_core_rw ./gradlew test --no-daemon`이 성공하지만 `:test UP-TO-DATE`로 표시됩니다.
- 원인: 테스트가 런타임에 읽는 `docs/` 파일의 변경이 현재 Gradle test 입력에 포함되지 않을 수 있습니다. 문서 변경만으로 테스트 재실행이 보장되지 않습니다.
- 대응: 문서 계약을 확인할 때 `test --rerun-tasks --no-daemon`으로 실제 재실행하고, 테스트 결과와 skip을 확인합니다. 테스트 입력/CI 구성 변경은 별도 작업입니다.
- 검증 결과는 [작업 현황](../phase-plan.md)에 기록합니다.

## Git 정리 도중 다른 작업이 같은 작업공간을 변경한 경우

- 문제: Git 정리의 백업·검증 중 현재 브랜치가 바뀌고 같은 안내 문서와 CI에 다른 편집이 추가됐습니다. 현재 파일 전체를 커밋하면 서로 다른 작업이 섞일 수 있습니다.
- 대응: 시작 시 보존한 patch·미추적 파일 압축본을 별도 worktree의 원래 브랜치에 복원하고 그 snapshot만 검증·커밋합니다. 원래 작업공간을 checkout·stash·reset으로 되돌리거나 새 편집을 덮어쓰지 않습니다.
- 보존: Git bundle은 기존 ref와 커밋의 백업이며 미커밋 파일의 백업이 아닙니다. 추적 파일 patch와 미추적 파일 내용을 따로 보존하고, 복원 검사와 index diff 확인을 함께 수행합니다.
- 브랜치 정리: 두 main 기준의 포함 여부·시작 bundle의 tip·현재 worktree·열린 PR을 확인한 명시 목록에만 `git branch -d`를 적용합니다. 미병합·새로 생성된 브랜치는 유지하고 `-D`로 우회하지 않습니다.
- 실제 환경·검증·정리 수량은 [작업 현황](../phase-plan.md#2026-10-22-git-정리와-리팩토링-기준점-보존)에 기록했습니다.

- 후속 정합화: 다른 worktree에서 커밋·푸시해도 원래 폴더의 HEAD와 미커밋 상태는 자동 변경되지 않습니다. 최신 변경을 다시 백업·대조하고 작업 파일을 그대로 둔 채 이미 보존한 커밋을 기준점으로 맞춘 뒤, 양쪽 기록과 이후 편집을 합쳐 추가분만 커밋합니다. 기준점 전환 전후에는 전체 추적·미추적 파일의 내용과 권한을 대조하며, 자세한 결과는 [원래 작업공간 통합 기록](../phase-plan.md#2026-10-22-원래-작업공간과-정리-브랜치-통합)을 확인합니다.

## 기록 형식

각 항목에는 필요한 내용만 남깁니다.

1. 증상과 재현 환경.
2. 확인한 원인과 근거.
3. 변경한 내용과 선택 이유.
4. 실제 실행한 검사와 결과.
5. 미확인 범위와 재발 방지 방법.
