# MVP 확장 플레이북

## 목적

이 문서는 현재 프로젝트를 `처음부터 완성형으로 만들지 않고`, 실제 운영 결과를 본 뒤 필요한 컴포넌트를 덧붙이는 방식으로 확장하기 위한 기준 문서다.

핵심 원칙은 아래와 같다.

1. 먼저 단순하게 만든다.
2. 지표와 로그를 붙여 실제 병목을 확인한다.
3. 문제가 재현되면 그 문제를 정확히 겨냥한 구성요소만 추가한다.
4. 아직 나타나지 않은 문제를 미리 큰 인프라로 해결하려고 하지 않는다.

---

## 지금 하지 말 것

아래 항목은 `문제가 확인되기 전까지는` 기본적으로 도입하지 않는다.

- 검색엔진(OpenSearch, Elasticsearch, Meilisearch, Typesense)
- 메시지 큐(Kafka, RabbitMQ, SQS)
- 별도 추천 파이프라인/벡터 DB
- read replica 다중화
- 복잡한 feature flag 플랫폼
- 별도 데이터 웨어하우스
- 고급 A/B 테스트 플랫폼
- 대규모 마이크로서비스 분리
- 관리자 MFA 강제
- WAF/Bot management 상용 서비스

이 항목들은 “언젠가 필요할 수 있음”과 “지금 필요함”을 구분해야 한다.

## 신호 보이면 붙일 것

### 1. 검색

#### 현재 기본 전략

- PostgreSQL FTS + `pg_trgm` + 필터 조합으로 유지
- 검색 API rate limit, 입력 길이 제한, 페이지 크기 제한으로 방어

#### 붙일 후보

- OpenSearch / Elasticsearch
- Meilisearch / Typesense
- 자동완성 인덱스
- synonym 사전
- typo tolerance
- 검색 전용 denormalized read model

#### 붙이는 신호

- 검색 결과 정확도가 낮다는 사용자 피드백이 반복된다
- 오타/유사어 검색 실패가 자주 나온다
- 필터 조합이 많아져 응답시간이 계속 느리다
- 인기 검색어, 자동완성, 검색 추천이 제품 요구로 명확해진다

#### 우선 도입 순서

1. synonym/오타 보정 규칙
2. 자동완성
3. 검색 전용 엔진

## 확인용 서버 권장 구조

### 현재 프로젝트 기준 판단

- 지금은 운영 서버 오픈 단계가 아니라 기능/구조 검증 단계다. [current-state.md](../current-state.md)
- 프론트 라우트 수가 작고, 현재 핵심 변화 축은 프론트보다 백엔드/수집/추천/보안 쪽에 더 가깝다.
- 관리자도 별도 웹 UI가 아니라 API 권한 중심이다.
- 현재 저장소도 `docker-compose.yml` 기준으로 `app + postgres + redis`를 한 번에 띄우는 구조를 기본값으로 두고 있다.

즉, 지금 확인용 서버의 목적은 `운영형 확장성 확보`가 아니라 `실제로 올려서 로그인/정책조회/추천/수집이 도는지 확인`하는 것이다.

### 현재 권장안

`1개 도메인 + 1대 서버 + Nginx + app/postgres/redis 동거`

예시:

- `https://test.example.com/` -> 프론트 정적 파일
- `https://test.example.com/api/*` -> Spring Boot
- PostgreSQL/Redis -> 같은 서버 내부 Docker 네트워크

### 왜 이렇게 잡는가

#### 1. CORS와 쿠키를 단순하게 유지하려고

- 프론트와 백엔드를 같은 origin 아래 두면 확인용 단계에서 CORS를 거의 신경 쓰지 않아도 된다.
- 로그인/refresh cookie 흐름도 더 단순해진다.
- 지금은 인증/세션/추천/북마크 같은 경계를 확인하는 단계라, origin을 늘려 복잡도를 키우는 이득이 작다.

#### 2. 프론트가 독립적으로 자주 변하는 구조가 아니기 때문에

- 현재 프론트는 라우트 수가 적고, 책임이 “백엔드 기능을 보여주는 얇은 화면”에 가깝다.
- 시간이 지나도 큰 축은 버그 수정, 문구 조정, API 필드 추가 반영, 상태 흐름 보정일 가능성이 높다.
- 따라서 지금부터 프론트/백엔드를 배포 구조까지 분리할 필요성이 크지 않다.

#### 3. 지금 필요한 것은 운영형 분리보다 확인 속도이기 때문에

- 지금은 “실제 서버에서 도는지”가 더 중요하다.
- 1대 서버에 같이 올리면 구성 요소가 적어서 문제를 빨리 드러내기 쉽다.
- 프론트, 백엔드, DB, Redis를 각각 다른 서비스로 나누면 확인용 단계에서 오히려 연결점만 늘어난다.

#### 4. 나중에 분리해도 구조적으로 막혀 있지 않기 때문에

- 백엔드는 이미 env 기반으로 외부 DB/RDS를 받을 수 있다.
- 나중에 필요하면 같은 앱 서버를 유지한 채 DB만 RDS로 빼는 전환도 가능하다.
- 즉 지금 단순하게 가는 것이 미래 선택지를 닫아버리는 건 아니다.

### 확인용 서버에서 기대하는 검증 범위

- 프론트 진입/로그인/회원가입/비밀번호 재설정
- 정책 목록/검색/상세/북마크
- 추천 조회/refresh
- 마이페이지 저장
- 관리자 계정으로 collect/replay/smoke API 확인

이 범위를 넘어서:

- 고가용성
- 무중단 배포
- read replica
- 외부 managed Redis
- 복수 도메인 분리

같은 것은 확인용 단계의 목표가 아니다.

### 지금 굳이 하지 않는 것

- 프론트 전용 별도 호스팅(Vercel 등)
- 백엔드 API 별도 서브도메인 분리
- RDS 강제 도입
- managed Redis 강제 도입
- 프론트/백엔드 별도 배포 파이프라인

의도:

- 아직 검증되지 않은 구조를 미리 운영형으로 쪼개지 않는다.
- 문제를 더 적은 구성요소에서 먼저 재현하고, 그 다음에 분리한다.

### 나중에 구조를 키울 시점

아래 신호가 오면 그때 2도메인 또는 인프라 분리를 검토한다.

- 프론트를 별도 호스팅/CDN에서 독립 배포하고 싶다
- 프론트 배포 빈도가 크게 늘어난다
- 모바일 앱이나 외부 클라이언트가 같은 API를 본격적으로 사용한다
- 앱 서버는 자주 갈아엎되 DB는 안정적으로 유지해야 한다
- 운영 환경에서 DB 백업/가용성 요구가 분명해진다

그때의 일반적인 순서는 아래다.

1. DB를 RDS로 분리
2. 필요하면 Redis를 managed로 분리
3. 프론트 전용 호스팅 또는 별도 도메인 분리
4. 외부 uptime/에러 알림 도입

### 현재 결론

지금 이 프로젝트의 확인용 서버 목적에 가장 맞는 구조는 `1개 도메인 + 1대 서버 + app/postgres/redis 동거`다.

이 선택의 의도는:

- 빠르게 띄우고
- 인증/정책/추천/수집이 실제 서버에서 도는지 보고
- 운영형 분리는 실제 필요가 확인된 뒤에만 추가하기 위함이다.

- read replica
- queue/worker 분리

## 최종 원칙

이 프로젝트는 “완성형 구조를 먼저 설계하는 방식”보다 “간단하게 운영하고, 실제 병목이 보이면 그 병목만 증설하는 방식”이 맞다.

따라서 어떤 기능이나 인프라를 붙이기 전에는 반드시 아래 질문을 먼저 본다.

1. 지금 실제로 문제가 재현됐는가?
2. 로그와 지표로 병목 위치가 확인됐는가?
3. 더 작은 수정으로 해결 가능한가?
4. 새 구성요소가 운영 복잡도를 얼마나 늘리는가?

이 네 질문에 답한 뒤 붙인다.
