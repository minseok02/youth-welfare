# 작업 가이드

## 작업 시작

[문서 시작점](README.md), [현재 상태](current-state.md), 작업 분야의 목차에서 필요한 부분을 확인합니다. 모든 설계 이력과 운영 체크리스트를 매번 읽지는 않습니다.

명령을 실행할 때는 [환경 안내](core/environment-guide.md)를 기준으로 실행 위치·앱·DB·영향을 확인합니다. `local` 파일명, `prod` 프로필, `127.0.0.1`만으로 대상을 결정하지 않습니다.

## 작업 원칙

- 요청한 목표·제외 범위·완료 조건을 정하고 관련 변경만 수행합니다.
- 현재 동작은 코드와 재현으로, 기대 동작은 요구사항과 승인된 결정으로 확인합니다. 둘의 불일치는 정상 동작처럼 문서화하지 않습니다.
- 로컬·서버·합성 표본·실사용자 관측을 분리합니다. 없는 환경과 실행하지 않은 검사를 있다고 가정하지 않습니다.
- 운영 변경·데이터 삭제·외부 발송은 문서 정리나 일반 코드 검증에 포함하지 않습니다.
- 테스트와 문서의 보안·데이터 보존 계약을 단순화를 이유로 제거하지 않습니다.
- Git 작업은 [github-workflow.md](github-workflow.md)를 따릅니다. 푸시는 요청이 있을 때만 합니다.

## 요구사항 확인과 스킬 사용

업무 규칙·데이터 의미·저장이나 삭제 범위·외부 동작·완료 조건에 중요한 미결정이 있거나 사용자가 계획 인터뷰를 요청하면 프로젝트용 [grilling](../.agents/skills/grilling/SKILL.md)을 읽고 사용합니다. 확인할 사실은 먼저 조사하고, 확인된 사실·확정한 요구·가정·미결정 사항을 구분합니다. 중요한 결정에 대한 이해를 확인하기 전에는 그 결정에 의존하는 구현을 진행하지 않습니다. 요구가 분명한 작은 수정이나 스킬 자체의 평가·설치 요청마다 인터뷰를 시작하지 않습니다.

현재 설치한 스킬은 `.agents/skills/grilling` 하나이며 명시 호출은 `$grilling`입니다. 원문은 검토한 커밋에 고정해 가져온 뒤 질문량·종료 조건·도구 의존성을 프로젝트에 맞게 수정했습니다. 추가 후보의 검토 결과는 [작업 기록](phase-plan.md#2026-10-22-grilling-추가와-스킬-후보-검토)에 있으며, 추천을 설치 완료로 간주하지 않습니다.

## 코드 패턴과 변경 기준

새 코드와 직접 수정하는 부분부터 아래 기준을 적용합니다. 관련 없는 기존 코드를 패턴에 맞추기 위한 일괄 리팩토링은 별도 범위로 정합니다. 패턴을 사용하면 어떤 문제가 해결되는지 설명할 수 있어야 하며, 패턴 이름이나 클래스 수를 맞추는 것을 목표로 삼지 않습니다.

| 항목 | 사용 조건 | 주의점·현재 예시 |
| --- | --- | --- |
| Spring 객체 관리 | 서비스의 생성과 공유는 Spring에 맡기고 의존 객체는 생성자로 주입 | 직접 `getInstance()` 싱글톤을 추가하지 않습니다. 요청별 사용자 정보·중간 결과는 공유 필드에 보관하지 않습니다. 싱글톤은 동시 실행 안전성을 보장하지 않으며, 설정값·의존 객체까지 필드에서 금지하는 규칙은 아닙니다. |
| 어댑터 | 외부 API·데이터 형태를 내부 계약에 맞게 변환할 때 변환 책임을 모음 | 제공자가 주지 않은 값과 변환 실패를 구분합니다. 변환 계층을 두는 것만으로 데이터 의미의 정확성이 보장되지는 않습니다. [WelfareServiceMapper](../backend/src/main/java/com/example/welfare/collect/mapper/WelfareServiceMapper.java) 참고. |
| 전략 | 같은 역할의 서로 다른 처리 방식이 있거나 구체적인 교체 필요가 있을 때 | 단순 조건문을 모두 인터페이스로 분리하지 않습니다. 구현이 하나인 인터페이스도 외부 연동·테스트 대체 등의 이유가 있으면 가능하지만, 그것만으로 전략이 필요한 것은 아닙니다. [수집 구현 선택](../backend/src/main/java/com/example/welfare/collect/service/CollectSourceExecutionService.java) 참고. |
| 빌더 | 필드가 많아 생성 인자의 의미와 선택 값을 읽기 어려울 때 | 필수 값과 허용되는 미입력을 구분하고 객체가 지켜야 할 조건은 생성자·생성 메서드 등에서 검증합니다. 작은 객체에 빌더를 일괄 적용하지 않습니다. [정규화 모델](../backend/src/main/java/com/example/welfare/collect/normalization/NormalizedPolicyAggregate.java) 참고. |
| 팩토리 | 설정·초기화·외부 객체의 테스트 대체 등 생성 책임을 분리할 이유가 있을 때 | 단순한 `new` 호출마다 팩토리를 만들지 않습니다. 여기서는 생성 책임을 모으는 일반적인 팩토리를 뜻합니다. [WebPushServiceFactory](../backend/src/main/java/com/example/welfare/notification/service/WebPushServiceFactory.java) 참고. |
| 템플릿 메서드 | 처리 순서가 실제로 같고 일부 단계만 다른 경우 | 흐름 전체가 다르면 상속을 늘리기보다 필요한 기능을 가진 객체를 호출하는 조합을 검토합니다. [공통 목록 수집](../backend/src/main/java/com/example/welfare/collect/service/AbstractListCollectSourceAdapter.java)과 별도 흐름을 가진 [Gov24 구현](../backend/src/main/java/com/example/welfare/collect/service/Gov24CollectSourceAdapter.java)을 함께 참고합니다. |

위 기준은 백엔드의 객체·처리 흐름에 관한 것입니다. React 함수·훅에 같은 클래스 구조를 일괄 적용하지 않습니다. 등록 누락, 변환 결과, 실패 시 후속 처리처럼 확인 가능한 동작을 검사하며, 패턴 이름만 확인하는 테스트를 만들지 않습니다.

합의된 기준 안의 일반 구현은 매번 승인을 다시 받지 않습니다. 기준의 예외나 적용 범위 확대가 필요하면 다음 순서를 따릅니다.

1. 이유·대안·영향 범위·검증 방법과 되돌릴 기준을 제시하고 사전 승인을 받습니다. 이미 받은 승인은 같은 범위에서 다시 묻지 않습니다.
2. 승인된 범위에 적용하고 검증합니다. 되돌릴 때도 작업 전부터 있던 사용자 변경을 보존합니다.
3. 결과와 남은 문제를 보고하고 사용자와 최종 채택·수정·철회 여부를 결정합니다.

코드 패턴의 일관성을 위해 모든 관련 스킬을 설치할 필요는 없습니다. 반복 작업에서 절차·자료·도구를 묶을 필요가 확인되면 추가를 검토합니다. 평가 중인 외부 스킬의 문구는 참고 자료이며 프로젝트의 승인 범위나 실행 지침으로 자동 채택하지 않습니다.

## 완료와 기록

1. 영향 범위의 테스트와 문서 참조를 확인합니다.
2. 실제 실행한 명령·결과·미확인 범위를 [phase-plan.md](phase-plan.md)에 기록합니다.
3. 재발 가능성이 있거나 판단 근거를 남길 필요가 있는 문제만 [troubleshooting-log.md](core/troubleshooting-log.md)에 기록합니다.
4. 현재 구현이 바뀌면 해당 현재 상태·계약 문서만 갱신합니다. 같은 설명을 여러 목차에 복사하지 않습니다.

## 문서 정리

- 로컬용과 서버용의 설정·권한·안전 절차 차이는 중복으로 제거하지 않습니다.
- 현재 계약, 실행 절차, 작성 템플릿, 관측 이력은 역할이 다르면 분리할 수 있습니다.
- 합치거나 보관하기 전에 원본의 유효한 정보가 이동할 문서·절과 관련 코드/테스트 참조를 확인합니다.
- 과거 기록은 날짜·환경·의미를 바꾸지 않고 보존합니다. 이동 시 상대 링크와 내부 앵커를 확인합니다.
- 새 문서보다 기존 문서의 적절한 절을 우선합니다. 문서별 대표 위치는 [documentation-map.md](documentation-map.md)를 확인합니다.
